状态（2026-10-18更新）：原只读排查记录保留如下；用户随后明确要求“一起修复”，主线程已修正额度语义及请求/账号池处理并在本机8081上线。旧失效成员保持暂停，未恢复其凭据；新Business成员三协议实测成功。后续处置见第7节与[上线验收记录](2026-10-18-dashboard-upgrade-acceptance.md)。

## 1. 结论

当前要分别处理两个问题，不能合并成“积分用完导致 API 报错”：

1. **认证失败已确认，具体原因待定位。** 用户端出现外层 502；服务日志显示 Notion 上游实际返回 `401 UnauthorizedError`。尚未确认是 Cookie 失效、账号/工作区身份不匹配，还是其它认证条件变化。
2. **Premium 余额处理存在已确认的语义问题。** 代码在上游余额小于等于零时，用“总额减已用”替换它，无法区分真实零余额与缺失字段，因此面板的推算值不能直接当作上游确认的可用余额。

截图中的 `Premium 0 / 300` 本身表示已用/总额，不表示剩余为零。下方显示“剩余 300”，但这个值可能经过上述推算；既不能据此断言积分清空，也不能据此保证实际还可用 300。

## 2. 已核实的证据

### 2.1 本次请求错误

- 用户端：`502 notion API error: notion API error 401 ...`，客户端自动重试。
- 对本机服务日志尾部做了只读、脱敏检查，21:15:18、21:15:34、21:16:09 均有上游 401。
- 提取到的错误类型为 `UnauthorizedError`，消息为 `Something went wrong. (401)`。
- 没有读取或展示 Token、Cookie，没有为复现问题重复发送真实推理请求。

这证明失败发生在 Notion 上游认证层，不足以证明具体哪个池成员失效，也不足以把原因归为套餐额度耗尽。浏览器当前已登录，不代表之前导入账号池的凭据仍然有效。

### 2.2 余额推算代码

核对位置：`internal/proxy/notion.go` 的 `CheckQuota`，读取 V2 Premium 数据后：

```go
premiumRemaining := v2.PremiumCredits.TotalCreditBalance
if premiumRemaining <= 0 && monthlyLimit > monthlyUsage {
    premiumRemaining = monthlyLimit - monthlyUsage
}
```

`quotaV2Response` 中相关数值为普通整数，未区分缺失字段与明确返回的零。上述分支又将非正余额替换为推算值；若上游真实余额为零、但总额大于已用，仍会显示正余额。

这是数据解释与来源标记问题，尚未证明 Notion 的真实余额到底是多少，也未证明该分支导致了本次 401。

## 3. 待定位项

- 本次 401 实际命中的 AccountID，以及它对应的用户/工作区是否与保存的凭据一致。
- 同一登录会话的身份读取、额度读取、推理接口是否呈现不同认证结果；先核对现有证据，不盲目重复推理。
- Premium 原始响应中余额字段是明确的 `0`、缺失、`null`，还是其它结构；只保留脱敏结构和必要数值，不把完整响应或凭据写入文档、日志库或版本库。
- 当前服务是否仍展示上次成功刷新时的缓存值，以及检查时间、读取失败是否足够醒目。
- 当前运行版本在 401 时是否正确隔离该成员、保留最后已知额度，并避免对同一失效凭据反复调用。

## 4. 修正要求与协调边界

由主线程协调者按现有文件所有权安排，不在本侧对话联系或重新分配 agents。

- **共享额度/协议接线负责人：** 区分上游明确余额与缺失/未知；不得用推算覆盖真实零余额。若确需兼容估算，单独标注来源、计算依据和检查时间，不作为已核实的余额。
- **账号池负责人：** 401 归类为认证异常，不归为额度耗尽，不清零套餐数据；所有状态按 AccountID 隔离。同邮箱不同工作区不合并，继续按动态 N 账号池而非主备模式处理。
- **日志/分析负责人：** 保留外层响应状态与上游认证失败的区别；请求失败不计成功，账号尝试不冒充多次用户请求；只存安全错误分类，不能存原始凭据或请求正文。
- **前端负责人：** 明确标注“已使用/总额”“剩余”“未知/缓存/推算”；套餐额度与兼容 Basic/Premium 数据分开展示。认证异常应显示重新导入凭据等处理提示，不能显示为“积分归零”。

切号仍须遵守主升级计划的安全边界：已输出内容、已上传文件、可能执行写入或涉及工作区上下文时，不能只因出现 401 就透明跨工作区重放。不要为了验证切号而耗尽真实账号额度。

## 5. 必须补充的验收

- [ ] V2 明确余额为 `0`、总额为 `300`、已用为 `0`：保留明确零值，并标注相互矛盾或待核实；不得悄悄改成确认余额 `300`。
- [ ] V2 余额缺失或为 `null`：显示未知；兼容推算如保留，必须与真实余额区分。
- [ ] 额度读取失败：保留带时间的最后已知值或显示未知，不伪装为刚刷新成功或全部归零。
- [ ] Business 的套餐窗口仍有余量，但旧 Basic 超限或 Premium 为零：不能仅凭旧字段判定整个账号永久不可用；冲突应可见并待核实。
- [ ] 上游 401：明确记录认证失败，不改写成额度耗尽，不清零各额度字段；检查失效成员是否被重复选择。
- [ ] 对无输出、无副作用且允许切号的请求：其它合格池成员可继续服务；对不安全重放的请求明确终止。
- [ ] 同邮箱不同工作区的认证、额度及状态相互独立；覆盖多于两个账号的情况。
- [ ] 实际构建并更新运行服务后，在真实管理页面读回字段、时间和错误状态；少量推理连通性验证与额度耗尽演练分开，后者不做真实消耗测试。
